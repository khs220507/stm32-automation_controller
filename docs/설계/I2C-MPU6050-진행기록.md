# I2C·MPU6050 진행 기록

## 문서 목적

이 문서는 NUCLEO-F401RE와 SZH-EK007(GY-521형 MPU6050)의 I2C Bring-up 과정에서 현재 진행 위치와 다음 시작점을 남긴다. 공식 요구사항과 시험 판정의 원본은 `docs/records/펌웨어-프로젝트-요구사항.xlsx`이며, 이 문서가 이를 대체하지 않는다.

## 다음 대화에서 가장 먼저 할 일

1. 단순한 대화 재개·진행 위치 확인은 이 작업 기록만 확인한다.
2. 새 과제 또는 설계·구현·검토를 시작할 때 `VERSION`과 공식 요구사항 문서의 개정·상태를 확인한다.
3. 최신 재개 위치는 아래 **2026-09-09 SPI 1바이트 송수신 구현**과 [통신 경험 요약](../통신-경험과-채용공고-대응.md)의 진행 중 항목을 확인한다. I2C·가속도·GPIO 설명을 처음부터 반복하지 않는다.

현재 재개 위치는 **`spi2_configure()` 설명 후 `spi2_transfer_byte()` 구현을 마치고 코드 분석 시작 전**이다. 사용자가 구현본을 차근차근 분석하는 방식으로 진행한다. 각속도 수집은 아직 추가하지 않았다.

## 2026-09-09 SPI 1바이트 송수신 구현

- `spi2_configure()`를 마지막 SPE 활성화까지 설명하고 I2S, CS/NSS, 마스터·슬레이브, 클록 분주를 함께 살펴봤다. 사용자 요청에 따라 해당 함수의 핵심 주석만 남겼다. 별도 이해 평가를 수행한 것은 아니다.
- 사용자 명시 요청으로 `Src/spi2.c`에 `spi2_transfer_byte(tx, rx, timeout_us)`를 구현했다. TXE 확인 → DR 쓰기 → RXNE 확인 → DR 읽기 → TXE/BSY 종료 확인 순서이며, 성공 시에만 출력값을 갱신한다.
- 1 MHz timebase 동작이 전제이며 전체 대기에 공통 제한시간을 사용한다. 시간 초과·오류·이전 전송/수신 잔여 상태 발견 시 후속 호출을 차단한다. 호출자는 CS를 해제하고 MCU 재부팅 후 다시 시작한다. 자동 복구·재시도는 구현하지 않았다.
- 이 함수는 CS를 바꾸지 않는다. 향후 상위 프레임 처리에서 CS를 제어해야 한다. 현재 main 호출·W5500 읽기 명령·다운로드·실기 송수신은 추가하지 않았다. OK는 MCU 내부 송수신 완료이며 상대 연결 확인이 아니다.
- 검증: `cmake --build --preset Debug` 성공. `Tests/호스트-시험.ps1`의 SPI2·기존 I2C·MPU6050 호스트 시험 모두 성공. SPI 시험은 정상/연속 호출, 타이머 래핑, TXE/RXNE/BSY 시간 초과, 공통 시간 한도, 오류 발생, 출력값 보존, 잔여 상태·잘못된 인수·비활성 상태 거부, 실패 후 재호출 차단을 확인했다.
- 시험 모형은 실제 DR 읽기 부수 효과·핀 파형·센서 응답을 재현하지 않는다. 실제 송수신 검증 전이다. 공식 요구사항 문서의 상태는 변경하지 않았다.
- 근거: [RM0368 Rev 6](../references/rm0368-stm32f401xb-c-d-e-mb-reference-manual-stmicroelectronics.pdf), §20.3.3 Configuring the SPI in master mode p.569, §20.3.5 Data transmission and reception procedures p.573, §20.5.3 SPI status register p.605~606(FRE 8, BSY 7, OVR 6, MODF 5, CRCERR 4, TXE 1, RXNE 0), §20.5.4 SPI data register p.606(DR[7:0]). 문서·PDF 페이지 동일.
- 다음 작은 과제: 입력은 `spi2_transfer_byte()` 코드와 위 매뉴얼. 목적은 1바이트 송수신 순서와 실패 반환을 이해하는 것이다. 함수 인수 `tx`, `rx`, `timeout_us`부터 설명하고, 성공 시 출력 갱신과 실패 시 보존을 구분할 수 있으면 완료한다.

## 2026-09-09 SPI 설정 분석 대기

- 가속도 설정·읽기 함수 분석 완료. UART·WPF 내부의 추가 분석은 사용자가 생략하기로 했다.
- SPI2 클록과 GPIO 핀 설정 설명 완료. 통신 설정까지 구현한 뒤 다음 대화에서 분석하기로 했다.
- 다음 시작점: `firmware/automation_controller_vscode/automation_controller/Src/spi2.c`의 `spi2_configure()`. 큰 흐름부터 설명하고 레지스터 설명에는 문서 링크·개정·절·페이지를 안내한다.
- SPI 데이터 송수신·W5500 식별값 읽기·TCP는 아직 수행하지 않았다. 배선·전원/RDY 관찰·레지스터 확인 요약은 [통신 경험 요약](../통신-경험과-채용공고-대응.md)에 연결한다.

### 요청과 확인한 사실

- 사용자 요청: Codex가 가속도 수집부터 UI 확인까지 구현하고 사용자가 이후 코드를 단계별로 분석한다.
- 사용자는 기존 UI의 MPU6050 확인 성공과 SLEEP 변경 전 0x00/확인값 0x00을 보고했다. 이는 이미 SLEEP=0이었다는 관찰이며, 1→0 전환 시험이나 가속도 측정 성공의 증거는 아니다. 추가 파형·화면 파일은 제공받지 않았다.
- VERSION은 프로젝트 0.1.0-draft, 요구사항 0.2-draft. 공식 Excel에서 FW-REQ-013/019/022는 의뢰, FW-REQ-047은 합의를 확인했다. 현재 요청 범위로 구현했으며 공식 관리 문서와 승인 상태는 변경하지 않았다.

### 구현 흐름과 근거

1. WPF `가속도 측정 시작` → `CONFIG_ACCEL`: WHO_AM_I=0x72 확인 후 센서 설정을 읽기/쓰기/재읽기로 확인한다. 현재 모듈의 레지스터 호환을 전제로 하며 칩 종류나 정확도를 확정하지 않는다.
2. `mpu6050_accel_configure()`: SLEEP/CYCLE 해제, 내부 발진기, 가속도 세 축 활성화, 자가시험 해제, ±2g, DLPF=3, SMPLRT_DIV=9, DATA_RDY 활성화. 다른 필드는 보존한다. 필터와 샘플레이트는 자이로에도 공유된다.
3. 초기 100 ms는 메인 루프를 막지 않고 대기한다. 이 값은 학습용 초기 대기이며 정밀 안정화 보증값이 아니다. 이후 설정 일치와 새 DATA_RDY를 확인한다.
4. `i2c1_read_registers()`가 0x3B~0x40의 6바이트를 한 번에 읽는다. 3~14바이트를 지원하며 1바이트는 기존 함수, 2바이트는 지원하지 않는다. 마지막 3바이트의 BTF→ACK 해제→읽기→BTF→STOP→나머지 읽기 순서를 구현했다. 성공한 경우에만 출력 버퍼를 갱신한다.
5. `mpu6050_accel_read()`가 상위/하위 바이트를 signed 16비트 XYZ로 결합한다. `OK,READ_ACCEL,x,y,z`의 부호 있는 10진수로 보내고 WPF가 16384로 나눠 g로 표시한다.
6. 센서 내부 갱신 설정은 명목 100 Hz이며, PC는 250 ms 간격으로 요청한다. 가속도만 실행하면 최대 약 4회/초, 초음파와 함께 실행하면 번갈아 요청하므로 각 약 2회/초다. 내부 표본 전체를 저장하는 수집기나 진동 분석 기능은 아니다.

근거:

- [로컬 MPU6050 Register Map Rev 3.2](../references/RM-MPU-6000A.pdf): p.10 §4.2 Sample Rate Divider, p.11 §4.3 Configuration, p.13~14 §4.5 Accelerometer Configuration, p.29~30 Interrupt Enable/Status, p.31 §4.23 Accelerometer Measurements, p.44~46 Power Management 1/2.
- 로컬 p.31의 감도 단위는 `LSB/mg`로 기재되어 있다. [제조사 Register Map Rev 4.2](https://invensense.tdk.com/wp-content/uploads/2015/02/MPU-6000-Register-Map1.pdf)의 Accelerometer Measurements 표에서 ±2g의 **16384 LSB/g**를 대조했다. 이번 환산은 이 단위를 사용한다.
- [로컬 RM0368 Rev 6](../references/rm0368-stm32f401xb-c-d-e-mb-reference-manual-stmicroelectronics.pdf): p.483~484 Controller receiver, `For N > 2-byte reception` 종료 절차.

### 오류 처리와 소프트웨어 시험

- 전송별 제한 10 ms, 실패 정리 추가 최대 1 ms. 설정은 최대 19회 전송. 측정은 설정 확인 6회, 이전 상태 해제 1회, 새 데이터 대기 최대 30 ms, 연속 읽기 1회다. 반복 대기에서도 남은 제한시간을 적용한다.
- 오류는 `ERR,CONFIG_ACCEL,...` 또는 `ERR,READ_ACCEL,...`로 반환한다. 실패한 표본을 내보내지 않고 설정 유효 상태를 해제한다. UI는 반복을 멈추고 원시값/g를 지운다. 다시 시작하면 설정부터 확인한다.
- UI 정지는 진행 중인 한 응답까지 처리한 뒤 마지막 값과 수신 시각을 보관한다. 연결 해제/READY/FAULT는 값과 반복을 무효화한다. 식별 확인과 가속도 측정은 같은 센서의 대체 시험이며 초음파 반복은 독립적으로 유지한다.
- ARM Debug 빌드 성공. 호스트 시험 두 실행 파일 성공: 3~14바이트 수신 종료 순서, PRIMASK 복원, 타이머 래핑, 부분 결과 보존, 통신 오류, 설정 읽기/쓰기/재읽기 실패, 식별값/리셋/설정 변경 검사, 데이터 시간 초과, signed 경계값, 실제 명령 처리 및 UART 문자열을 확인했다.
- 저수준 호스트 모형은 DR 읽기의 하드웨어 부수 효과를 재현하지 않는다. 같은 바이트로 제어 순서를 시험하고 서로 다른 바이트의 XYZ 결합은 센서 모형 시험에서 확인했다. SCL/SDA 파형과 실기 인터럽트 타이밍은 별도 확인 대상이다.
- WPF 자동 시험 **96개 통과**. 모의 XYZ 표시와 최소 폭 렌더, 시작 전 설정 순서, 정지 중 응답, 초음파 병행, 오류/재시작/해제, PC 500 ms 시간 초과 및 늦은 응답 무시를 확인했다. 첫 빌드는 실행 중인 기존 WPF 파일 잠금으로 실패했고 정상 종료 후 재빌드·시험이 성공했다.
- 결과: `software/build/test-results/accelerometer.trx`, `software/build/UltrasonicMonitor.Tests/bin/Debug/net10.0-windows/가속도-모의응답-화면.png`. 화면은 **모의 응답이며 실측이 아니다**. 새 펌웨어 다운로드와 실제 가속도 시험은 수행하지 않았다.
- 갱신한 WPF 실행 파일을 실행했다. 실제 시험은 COM 연결 후 사용자가 수행한다.

### 다음 작은 과제

- 제출할 결과: 정지/기울임 상태의 XYZ 원시값과 g, RX 원문 또는 화면. 오류가 있으면 코드도 그대로 남긴다.

- 다음 코드 분석 시작점: `app_state_run()`의 CONFIG_ACCEL 분기 → `mpu6050_accel_configure()`의 식별값 확인부터 작은 구간씩 설명한다. 퀴즈는 내지 않는다.

### 오늘 함께 본 내용

## 현재 모듈의 식별 기대값 0x72 반영

- 사용자가 기존 합의의 누락을 지적하여 PC의 식별 판정과 화면 기대값·색상을 0x72 기준으로 수정했다. 한 상수를 공유해 표시와 판정이 어긋나지 않게 했다. 10진수 응답 114는 성공, 104(0x68)는 현재 모듈 기준 불일치로 처리한다.
- 장치 주소 0x68과 WHO_AM_I 레지스터 주소 0x75는 유지한다. 제조사 문서의 기본 식별값을 변경하거나 실제 칩 호환성을 확정한 것은 아니다.
- WPF 자동 시험 78개 통과. 결과: `software/build/test-results/identity-72-tests.trx`. 펌웨어 변경은 없으며 실제 센서 확인은 사용자 수행 전이다. 아래 이전 기록의 기대값 미반영 문장은 당시 상태다.

## SLEEP 해제와 재읽기 확인 구현

- 사용자 요청으로 `app_state_wake_mpu6050()`를 추가했다. 로컬 `RM-MPU-6000A.pdf` Rev 3.2, 44~45쪽 4.36절을 근거로 장치 주소 0x68의 PWR_MGMT_1(0x6B)을 읽고 bit 6(SLEEP)만 0으로 만든 값을 쓴 뒤 다시 읽는다. 전체 바이트가 기대값과 같아야 성공이며 다른 비트 변경도 불일치로 처리한다.
- bit 7(DEVICE_RESET)이 1이면 SENSOR_RESET을 반환하고 쓰지 않는다. 쓰기나 확인 단계 실패 후 자동 재전송·복원은 하지 않는다. 실패 응답이어도 센서 설정은 이미 변경됐을 수 있다.
- 새 UART 명령 `WAKE_MPU6050`은 IDLE에서만 실행하며 기존 CHECK_MPU6050은 식별값 읽기를 유지한다. 오류 코드 문자열 변환은 공통 함수로 정리했다. WPF 버튼과 파서는 이번 범위에 포함하지 않았다.
- 구현된 임시 명령 형식: 요청 `WAKE_MPU6050\r\n`, 성공 `OK,WAKE_MPU6050,<변경 전 10진수>,<재읽기 10진수>\r\n`, 실패 `ERR,WAKE_MPU6050,<오류 코드>\r\n`. 예시 `OK,WAKE_MPU6050,64,0`은 0x40→0x00을 뜻하며 실제 계측값이 아니다. VERIFY_FAILED는 재읽기 불일치다. 이 설명은 공식 통신 규격서 개정·승인 기록이 아니다.
- 각 I2C 전송은 10 ms 한도이며 최대 3회다. 실패한 전송의 정리는 최대 1 ms 추가 대기한다. 총 31 ms는 루프·함수·초기화·UART 송신 오버헤드를 제외한 대기 예산 상한이며 실측값이 아니다.
- 검증: ARM GCC Debug 빌드·ELF 링크 성공, 호스트 시험 전체 통과. 정상 0x40→0x00, CYCLE/TEMP_DIS/CLKSEL 보존, 이미 SLEEP=0, 리셋 진행 중 쓰기 금지, 센서가 쓰기를 무시하는 경우, 다른 비트 불일치, 세 전송 각각의 NACK·시간 초과, BUSY/NOT_READY, AUTO 상태 거부, 오류 후 PING 응답을 모의했다. 실제 센서 호환성·안정화·파형·측정 정확도는 검증하지 않았다.
- 실기 시험 시 사용자가 새 ELF를 다운로드한 뒤 WPF COM 연결을 해제하고 시리얼 터미널(115200, 8N1, 흐름 제어 없음, CRLF)에서 IDLE 상태로 명령을 1회 보낸다. 전원 인가 전 기존 3V3/GND/PB8/PB9 배선의 극성·단락을 확인하고 24V는 사용하지 않는다. 변경 전·후 실제 응답과 파형을 보존한다. 현재 모듈의 식별값 0x72와 MPU6050 레지스터 호환성은 이 시험으로 따로 확인해야 한다.
- 다음 설명 위치: `app_state_wake_mpu6050()`의 현재 값 읽기 → SLEEP 비트만 지우기 → 쓰기 → 재읽기 비교. SLEEP 해제 확인은 센서 전체 초기화나 가속도·각속도 수집 완료를 뜻하지 않는다. CYCLE·클록 선택·축 대기 설정과 측정 안정화 시간은 다음 측정 단계에서 다룬다.

## 레지스터 쓰기 함수 추가

- 사용자는 I2C 초기화·정상 읽기·실패 정리 흐름을 함께 본 뒤 다음 구현을 요청했다. 설명은 퀴즈 없이 작은 코드 구간별로 진행하며, WPF 설명은 현재 학습 대상에서 제외한다.
- `i2c1_write_register(address, reg, value, timeout_us)`를 추가했다. START → 쓰기 주소/ACK → 레지스터 주소/ACK → 데이터/ACK → STOP 순서이며 반복 START와 수신 단계는 없다. 섹션별 짧은 한글 주석을 사용했다.
- 읽기 함수와 같은 초기화·메인 루프 단독 호출 조건, 전체 전송 제한시간 및 오류 정리를 적용했다. 오류 후 자동 재전송은 하지 않는다. 실패해도 센서가 이미 데이터를 받았을 수 있고, 성공은 설정값 적용 확인을 뜻하지 않는다.
- 근거: 로컬 RM0368 Rev 6, 481~482쪽 Controller transmitter. 로컬 `RM-MPU-6000A.pdf`는 Rev 3.2이며 PWR_MGMT_1은 44쪽 4.36절이다. 온라인 Rev 4.2의 페이지 번호와 혼용하지 않는다.
- 검증: ARM GCC Debug 빌드·ELF 링크 성공. `Tests/호스트-시험.ps1` 통과. 새 쓰기 시험은 전송 순서와 여러 데이터값, 타이머 래핑, 단계별 시간 초과, NACK/BERR/ARLO/OVR, 정리 후 다음 요청, BUSY 지속, 잘못된 인수 및 정지한 타이머를 포함한다. 기존 읽기·프로토콜·상태 시험도 통과했다.
- 모의 시험의 RCC 리셋은 일반 메모리 구조체에 자동 반영되지 않아 재시도 전에 SR1/SR2 리셋 결과와 버스 해제를 시험 코드에서 모의했다. 실제 하드웨어 리셋·전기적 파형 검증은 아니다.
- 실제 다운로드·쓰기 파형·센서 설정 읽기 복원 확인은 수행하지 않았다. 공식 요구사항·시험 판정 문서는 수정하지 않았다.
- 다음 설명 위치: `i2c1_write_register()`에서 `I2C1->DR = reg` 다음에 `I2C1->DR = value`를 보내는 차이. 다음 기능 단계는 PWR_MGMT_1 읽기·설정·재읽기 확인이며, 식별값 0x72인 모듈의 레지스터 호환성은 아직 검증되지 않았다.

## 2026-09-08 로직 분석기 캡처와 식별값 결정

- 사용자 수행: USB 로직 분석기를 설치하고 PulseView에서 캡처했다. Windows에서 장치 이름 fx2lafw, WinUSB 드라이버를 확인했다. 정확한 분석기 제조사·모델과 입력 정격은 확인하지 않았다.

- 사용자 제공 해독 화면: START → 주소 0x68 쓰기/ACK → 레지스터 0x75/ACK → 반복 START → 주소 0x68 읽기/ACK → 데이터 0x72 → NACK → STOP. WPF에서 관찰한 0x72와 버스 해독값이 일치했다.
- 제조사 MPU6050 문서의 WHO_AM_I 기대값은 0x68이며 실제 해독값은 0x72다. 이 차이만으로 실제 칩 종류, 호환성, 가품 여부 또는 측정 정확도를 확정하지 않는다.

- 코드 상태: 이번 마무리에서는 기대값을 수정하지 않았다. PC 파서의 기대값은 아직 0x68이므로 0x72를 ID_MISMATCH로 표시한다. 다음 작업은 해당 모듈용 기대값과 관련 표시·시험을 함께 수정하는 것이다. I2C 장치 주소 0x68과 WHO_AM_I 레지스터 주소 0x75는 유지한다.
- 증거: [원본 캡처](../MPU6050_식별값_0x72.sr), [PulseView 설정](../MPU6050_식별값_0x72.pvs). 이번 진행 메모는 공식 요구사항·시험 기록 원본을 대체하지 않는다.

## 2026-09-07 클록 트리·I2C 타이밍 학습

- 이번 대화에서 참조한 코드는 `firmware/automation_controller_vscode/automation_controller/Src/i2c1.c`와 같은 프로젝트의 `Src/system_stm32f4xx.c`다. 아래의 기존 핀 검증 절차와 코드 경로는 이전 기록이다.

- HPRE 비트 7:4와 PPRE1 비트 12:10 추출, 분주 설정 코드와 실제 분주비의 차이, AHBPrescTable·APBPrescTable을 통한 시프트 횟수 변환을 설명했다.
- 부호 없는 정수의 `>> 2`는 ÷4의 몫을 구한다. `pclk1_hz`는 HCLK와 APB1 분주 설정에서 계산한 Hz 단위 값이다.
- 사용자는 `SystemCoreClockUpdate()`부터 PCLK1 계산 및 입력 범위 검사까지 이해 완료라고 명시했다. 검사 조건은 2~42 MHz이며, 정수 MHz만 지원하는 조건은 현재 구현의 제한이다.
- 이후 CR2(Control Register 2)의 FREQ 비트 5:0에 입력 클록을 MHz 단위로 알리는 역할과 CCR(Clock Control Register)로 표준 모드 SCL 타이밍을 정하는 역할을 설명했다. 이 후반 범위는 설명을 진행한 상태이며 별도의 이해 완료 응답은 아직 없다.
- 계산 예시: HSI 명목 16 MHz, AHB ÷1, APB1 ÷1이면 PCLK1 = 16 MHz, CR2 FREQ = 16이다. 목표 SCL 100 kHz에서 CCR = ceil(16,000,000 / (2 × 100,000)) = 80이며, 이상적인 LOW·HIGH 시간은 각각 5 μs다.
- `(pclk1_hz + 199999U) / 200000U`는 양의 정수 올림 나눗셈으로 CCR을 구하는 식이다.
- 위 수치는 설정 조건에 따른 계산 예시다. 이번 대화에서 빌드·다운로드·레지스터 실관찰·SCL 파형 측정은 수행하지 않았으며 시험 통과로 판정하지 않았다.

다음 작은 학습 과제는 `I2C1->TRISE = (pclk1_hz / 1000000U) + 1U;`의 의미다. 입력은 현재 코드와 RM0368의 TRISE 설명이며, 완료 조건은 상승시간 설정과 CCR의 주기 설정을 구분하고 16 MHz 조건에서 TRISE = 17이 되는 계산을 설명하는 것이다.

## 핀 초기화 검증 절차

1. CubeIDE에서 프로젝트를 Refresh한다.
2. Project Clean 후 Build한다.
3. [app_state.c](../../firmware/automation_controller/Src/app_state.c)의 `i2c1_pins_init()` 다음 줄에 중단점을 설정한다.
4. Debug를 시작하고 중단점에서 다음 표현식을 관찰한다.

```c
(RCC->AHB1ENR >> 1) & 0x1U
(GPIOB->MODER >> 16) & 0xFU
(GPIOB->OTYPER >> 8) & 0x3U
(GPIOB->OSPEEDR >> 16) & 0xFU
(GPIOB->PUPDR >> 16) & 0xFU
GPIOB->AFR[1] & 0xFFU
(GPIOB->IDR >> 8) & 0x3U
```

기대값:

| 관찰 항목 | 기대값 | 의미 |
|---|---:|---|
| GPIOB 클록 | `0x1` | GPIOB 활성화 |
| MODER8·9 | `0xA` | PB8/PB9 Alternate Function |
| OTYPER8·9 | `0x3` | PB8/PB9 Open-drain |
| OSPEEDR8·9 | `0xA` | PB8/PB9 High speed |
| PUPDR8·9 | `0x0` | 내부 pull-up/down 없음 |
| AFR8·9 | `0x44` | PB8/PB9 AF4 |
| IDR8·9 | `0x3` | SCL/SDA 유휴 High |

I2C1 주변장치를 아직 활성화하지 않았으므로 이 단계에서는 SCL 클록 펄스가 없어야 한다. 레지스터 관찰값과 실제 SCL/SDA 전압을 확인하기 전에는 핀 초기화를 통과로 판정하지 않는다.
