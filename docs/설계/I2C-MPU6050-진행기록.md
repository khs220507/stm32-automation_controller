# I2C·MPU6050 진행 기록

## 문서 목적

이 문서는 NUCLEO-F401RE와 SZH-EK007(GY-521형 MPU6050)의 I2C Bring-up 과정에서 현재 진행 위치와 다음 시작점을 남긴다. 공식 요구사항과 시험 판정의 원본은 `docs/records/펌웨어-프로젝트-요구사항.xlsx`이며, 이 문서가 이를 대체하지 않는다.

## 다음 대화에서 가장 먼저 할 일

1. 단순한 대화 재개·진행 위치 확인은 이 작업 기록만 확인한다.
2. 새 과제 또는 설계·구현·검토를 시작할 때 `VERSION`과 공식 요구사항 문서의 개정·상태를 확인한다.
3. 아래 **레지스터 쓰기 함수 추가**에서 이어간다. 초기화와 1바이트 읽기 설명을 처음부터 반복하지 않는다.

현재 재개 위치는 **초기화·1바이트 읽기·실패 정리 학습 후, 센서 설정을 위한 1바이트 쓰기 함수 구현 및 소프트웨어 시험 완료**다. 실제 센서 설정 호출과 가속도·각속도 수집은 아직 추가하지 않았다. 식별값 0x72를 연결 확인 기대값으로 받아들이기로 한 결정은 유지하며 PC 코드 반영은 남아 있다.

## 레지스터 쓰기 함수 추가

- 사용자는 I2C 초기화·정상 읽기·실패 정리 흐름을 함께 본 뒤 다음 구현을 요청했다. 설명은 퀴즈 없이 작은 코드 구간별로 진행하며, WPF 설명은 현재 학습 대상에서 제외한다.
- `i2c1_write_register(address, reg, value, timeout_us)`를 추가했다. START → 쓰기 주소/ACK → 레지스터 주소/ACK → 데이터/ACK → STOP 순서이며 반복 START와 수신 단계는 없다. 섹션별 짧은 한글 주석을 사용했다.
- 읽기 함수와 같은 초기화·메인 루프 단독 호출 조건, 전체 전송 제한시간 및 오류 정리를 적용했다. 오류 후 자동 재전송은 하지 않는다. 실패해도 센서가 이미 데이터를 받았을 수 있고, 성공은 설정값 적용 확인을 뜻하지 않는다.
- 근거: 로컬 RM0368 Rev 6, 481~482쪽 Controller transmitter. 로컬 `RM-MPU-6000A.pdf`는 Rev 3.2이며 PWR_MGMT_1은 44쪽 4.36절이다. 온라인 Rev 4.2의 페이지 번호와 혼용하지 않는다.
- 검증: ARM GCC Debug 빌드·ELF 링크 성공. `Tests/호스트-시험.ps1` 통과. 새 쓰기 시험은 전송 순서와 여러 데이터값, 타이머 래핑, 단계별 시간 초과, NACK/BERR/ARLO/OVR, 정리 후 다음 요청, BUSY 지속, 잘못된 인수 및 정지한 타이머를 포함한다. 기존 읽기·프로토콜·상태 시험도 통과했다.
- 모의 시험의 RCC 리셋은 일반 메모리 구조체에 자동 반영되지 않아 재시도 전에 SR1/SR2 리셋 결과와 버스 해제를 시험 코드에서 모의했다. 실제 하드웨어 리셋·전기적 파형 검증은 아니다.
- 실제 다운로드·쓰기 파형·센서 설정 읽기 복원 확인은 수행하지 않았다. 공식 요구사항·시험 판정 문서는 수정하지 않았다.
- 다음 설명 위치: `i2c1_write_register()`에서 `I2C1->DR = reg` 다음에 `I2C1->DR = value`를 보내는 차이. 다음 기능 단계는 PWR_MGMT_1 읽기·설정·재읽기 확인이며, 식별값 0x72인 모듈의 레지스터 호환성은 아직 검증되지 않았다.

## 2026-09-08 로직 분석기 캡처와 식별값 결정

- 사용자 수행: USB 로직 분석기를 설치하고 PulseView에서 캡처했다. Windows에서 장치 이름 fx2lafw, WinUSB 드라이버를 확인했다. 정확한 분석기 제조사·모델과 입력 정격은 확인하지 않았다.
- 측정 위치: 기존 NUCLEO-F401RE와 MPU6050 모듈 사이의 SCL(D15/PB8), SDA(D14/PB9), 공통 GND. 사용자는 분석기 CH1을 SCL, CH2를 SDA에 연결했다고 확인했고 화면에서는 D0=SCL, D1=SDA로 해독했다.
- 조건: WPF의 MPU6050 반복 확인을 사용한 식별 레지스터 읽기. 저장 파일 메타데이터는 1 MHz, 8채널, 1,000,000 샘플(1초)이다. 전원 실측값과 SCL 주파수 실측값은 이번 대화에 제공되지 않았다.
- 사용자 제공 해독 화면: START → 주소 0x68 쓰기/ACK → 레지스터 0x75/ACK → 반복 START → 주소 0x68 읽기/ACK → 데이터 0x72 → NACK → STOP. WPF에서 관찰한 0x72와 버스 해독값이 일치했다.
- 제조사 MPU6050 문서의 WHO_AM_I 기대값은 0x68이며 실제 해독값은 0x72다. 이 차이만으로 실제 칩 종류, 호환성, 가품 여부 또는 측정 정확도를 확정하지 않는다.
- 사용자 결정: 현재 모듈의 연결 확인에서는 0x72를 정상 식별 응답으로 받아들인다. 이는 해당 모듈에 대한 운용 결정이며 공식 요구사항 변경이나 센서 측정 기능의 시험 통과를 뜻하지 않는다.
- 코드 상태: 이번 마무리에서는 기대값을 수정하지 않았다. PC 파서의 기대값은 아직 0x68이므로 0x72를 ID_MISMATCH로 표시한다. 다음 작업은 해당 모듈용 기대값과 관련 표시·시험을 함께 수정하는 것이다. I2C 장치 주소 0x68과 WHO_AM_I 레지스터 주소 0x75는 유지한다.
- 증거: [원본 캡처](../MPU6050_식별값_0x72.sr), [PulseView 설정](../MPU6050_식별값_0x72.pvs). 이번 진행 메모는 공식 요구사항·시험 기록 원본을 대체하지 않는다.
- 참고: [제조사 레지스터 문서](https://invensense.tdk.com/wp-content/uploads/2015/02/MPU-6000-Register-Map1.pdf), [동일 식별값 사용자 보고](https://forum.pjrc.com/index.php?threads/not-initialize-mpu6050-failed-to-find-mpu6050-chip.67594/). 포럼의 식별 검사 변경 사례는 정확도 검증 근거로 사용하지 않는다.

## 2026-09-07 MPU6050 식별 진단과 WPF 연결

- 사용자 요청: Codex가 직접 개발하고 사용자가 설명을 따라간다. 힌트·퀴즈 및 함수마다 중단점 시험을 요구하지 않고, UI까지 연결한 기능 단위로 함께 시험한다.
- 대상 F/W는 `firmware/automation_controller_vscode/automation_controller`, PC 앱은 `software/UltrasonicMonitor`다. 이전 CubeIDE 프로젝트에는 이번 변경을 복사하지 않았다.
- `i2c1_read_register()`는 단일 컨트롤러의 1바이트 레지스터 읽기를 구현한다. START, 쓰기 주소, 레지스터 선택, 반복 START, 읽기 주소, ACK 해제/ADDR 해제/STOP 요청, 데이터 수신, STOP 완료 순서다.
- MPU6050 진단은 7비트 주소 `0x68`(AD0=LOW 가정), `WHO_AM_I` 레지스터 `0x75`를 읽는다. 측정 모드/센서 설정은 변경하지 않는다.
- 전송 대기 예산은 10 ms, 실패 후 STOP/내부 리셋 정리의 추가 대기는 최대 1 ms다. 이는 반복문/함수 실행 오버헤드를 제외한 구현 설정이며, 실측값이 아니다. 타이머는 현재 HSI 명목 16 MHz 기반의 1 MHz TIM5 연속 동작을 전제로 한다.
- 오류는 BUS_BUSY, TIMEOUT, NACK, BUS_ERROR, ARBITRATION_LOST, OVERRUN, NOT_READY로 구분한다. 오류 경로에서는 출력 식별값을 갱신하지 않는다. 내부 I2C 리셋은 외부 장치가 SDA/SCL을 LOW로 잡는 고장을 복구하지 않는다.
- 초기화 시 UART를 I2C보다 먼저 준비하여 기동 FAULT에서도 진단/상태 조회가 가능하다. 진단 성공만으로 FAULT 상태를 해제하지 않는다.
- 기존 WPF에 MPU6050 연결 확인 버튼, 실제 식별값, 결과, 마지막 확인 시각을 추가했다. 식별값 `0x68`만 확인 성공이며 다른 값은 불일치로 표시한다. 센서 오류, PC 응답 시간 초과, 연결 해제 및 보드 재시작 시 이전 식별값을 지운다.

### 이번 코드에서 추가한 통신 형식

아래는 구현 설명이며, 공식 요구사항/통신 규격서 개정 또는 승인 기록을 대체하지 않는다. 공식 Excel 문서는 수정하지 않았다.

| 구분 | CRLF를 제외한 ASCII 라인 | 의미 |
|---|---|---|
| 요청 | `CHECK_MPU6050` | 식별 레지스터 1회 읽기 |
| 읽기 성공 예시 | `OK,CHECK_MPU6050,104` | 실제 읽은 10진수 값 104 = 0x68 |
| 식별값 불일치 예시 | `OK,CHECK_MPU6050,112` | 읽기는 성공했지만 0x70은 기대 ID와 다름 |
| 오류 예시 | `ERR,CHECK_MPU6050,NACK` | 센서 ACK 응답 없음 |

- 모든 라인은 CRLF로 끝나며 기존 64바이트 한도 안에 들어간다. 위 응답들은 형식 예시이며 실제 센서 측정값이 아니다.
- PC의 500 ms 응답 시간 초과와 MCU의 센서 통신 TIMEOUT을 별도로 표시한다.
- 기존 프로토콜에는 요청 번호가 없으므로 시간 초과 후 재요청 중 도착하는 같은 명령의 지연 응답을 완전히 구분할 수 없다. 보드를 중단점에서 멈춘 채 통합 시험하지 않는다.

## 2026-09-07 버스 유휴 대기 구현

- 사용자는 힌트·퀴즈 없이 Codex가 개발하고 사용자가 설명을 따라가는 방식을 요청했다. 초기화 후반 설명은 건너뛰었으며 이해 완료나 실기 통과로 판정하지 않았다.
- VS Code 프로젝트의 `i2c1.c`에 `i2c1_wait_idle(timeout_us)`를 추가했다. SR2 비트 1(BUSY)을 읽고, 버스가 유휴이면 true, 대기 제한시간을 넘기면 false를 반환한다. START/STOP 또는 버스 복구는 아직 수행하지 않는다.
- `app_state.c`에서 `timebase_init()` 이후 최대 1000 us 기다리도록 연결했다. 실패 시 안전 출력을 적용하고 FAULT로 진입한다. 1000 us는 실기 검증 전 임시 구현값이다.
- 전제는 I2C 초기화 성공, TIM5 기반 timebase의 1 MHz 연속 동작 및 동시 I2C 접근 없음이다. 현재 timebase의 분주 설정은 명목 16 MHz 타이머 입력을 전제로 한다.
- STM32Cube 번들의 CMake로 Debug 빌드가 성공했다. 변경한 두 C 파일의 컴파일과 ELF 링크를 확인했으며 해당 출력에 오류·경고는 없었다.
- 다운로드, 유휴·BUSY 지속 시 반환시간 측정, 타이머 오버플로 실기 시험은 수행하지 않았다.
- 다음 구현 위치는 유휴 확인 이후의 START 요청 및 제한시간을 갖는 시작 상태 확인이다. 버스 대기 함수의 실제 동작 검증은 남아 있다.

## 2026-09-07 클록 트리·I2C 타이밍 학습

- 이번 대화에서 참조한 코드는 `firmware/automation_controller_vscode/automation_controller/Src/i2c1.c`와 같은 프로젝트의 `Src/system_stm32f4xx.c`다. 아래의 기존 핀 검증 절차와 코드 경로는 이전 기록이다.
- RM0368 Figure 12의 HSI → 시스템 클록 선택기 → SYSCLK → AHB 분주기 → HCLK → APB1 분주기 → PCLK1 경로를 설명했다.
- 약어는 HSI(High-Speed Internal, 내부 고속 클록)처럼 풀 네임과 한국어 의미를 함께 설명하기로 했다.
- 하드웨어 분주기가 실제 클록을 나누며, 소프트웨어는 분주비를 설정하거나 현재 설정을 읽어 주파수를 계산한다는 차이를 설명했다.
- RCC CFGR의 SW 비트 1:0은 시스템 클록 선택 요청, SWS 비트 3:2는 실제 선택 상태다. 리셋 기본값은 HSI 선택, AHB·APB 분주비는 ÷1이며, 이번에 확인한 시작 코드에는 시스템 클록 선택을 바꾸는 코드가 없었다.
- `SystemCoreClockUpdate()`는 클록 소스와 AHB 분주 설정을 읽어 HCLK를 `SystemCoreClock` 변수에 계산한다. 실제 클록을 변경하는 함수가 아니다.
- HPRE 비트 7:4와 PPRE1 비트 12:10 추출, 분주 설정 코드와 실제 분주비의 차이, AHBPrescTable·APBPrescTable을 통한 시프트 횟수 변환을 설명했다.
- 부호 없는 정수의 `>> 2`는 ÷4의 몫을 구한다. `pclk1_hz`는 HCLK와 APB1 분주 설정에서 계산한 Hz 단위 값이다.
- 사용자는 `SystemCoreClockUpdate()`부터 PCLK1 계산 및 입력 범위 검사까지 이해 완료라고 명시했다. 검사 조건은 2~42 MHz이며, 정수 MHz만 지원하는 조건은 현재 구현의 제한이다.
- 이후 CR2(Control Register 2)의 FREQ 비트 5:0에 입력 클록을 MHz 단위로 알리는 역할과 CCR(Clock Control Register)로 표준 모드 SCL 타이밍을 정하는 역할을 설명했다. 이 후반 범위는 설명을 진행한 상태이며 별도의 이해 완료 응답은 아직 없다.
- 계산 예시: HSI 명목 16 MHz, AHB ÷1, APB1 ÷1이면 PCLK1 = 16 MHz, CR2 FREQ = 16이다. 목표 SCL 100 kHz에서 CCR = ceil(16,000,000 / (2 × 100,000)) = 80이며, 이상적인 LOW·HIGH 시간은 각각 5 μs다.
- `(pclk1_hz + 199999U) / 200000U`는 양의 정수 올림 나눗셈으로 CCR을 구하는 식이다.
- 위 수치는 설정 조건에 따른 계산 예시다. 이번 대화에서 빌드·다운로드·레지스터 실관찰·SCL 파형 측정은 수행하지 않았으며 시험 통과로 판정하지 않았다.

다음 작은 학습 과제는 `I2C1->TRISE = (pclk1_hz / 1000000U) + 1U;`의 의미다. 입력은 현재 코드와 RM0368의 TRISE 설명이며, 완료 조건은 상승시간 설정과 CCR의 주기 설정을 구분하고 16 MHz 조건에서 TRISE = 17이 되는 계산을 설명하는 것이다.

## 핀 초기화 검증 절차

1. CubeIDE에서 프로젝트를 Refresh한다.
2. Project Clean 후 Build한다.
3. [app_state.c](../../firmware/automation_controller/Src/app_state.c)의 `i2c1_pins_init()` 다음 줄에 중단점을 설정한다.
4. Debug를 시작하고 중단점에서 다음 표현식을 관찰한다.

```c
(RCC->AHB1ENR >> 1) & 0x1U
(GPIOB->MODER >> 16) & 0xFU
(GPIOB->OTYPER >> 8) & 0x3U
(GPIOB->OSPEEDR >> 16) & 0xFU
(GPIOB->PUPDR >> 16) & 0xFU
GPIOB->AFR[1] & 0xFFU
(GPIOB->IDR >> 8) & 0x3U
```

기대값:

| 관찰 항목 | 기대값 | 의미 |
|---|---:|---|
| GPIOB 클록 | `0x1` | GPIOB 활성화 |
| MODER8·9 | `0xA` | PB8/PB9 Alternate Function |
| OTYPER8·9 | `0x3` | PB8/PB9 Open-drain |
| OSPEEDR8·9 | `0xA` | PB8/PB9 High speed |
| PUPDR8·9 | `0x0` | 내부 pull-up/down 없음 |
| AFR8·9 | `0x44` | PB8/PB9 AF4 |
| IDR8·9 | `0x3` | SCL/SDA 유휴 High |

I2C1 주변장치를 아직 활성화하지 않았으므로 이 단계에서는 SCL 클록 펄스가 없어야 한다. 레지스터 관찰값과 실제 SCL/SDA 전압을 확인하기 전에는 핀 초기화를 통과로 판정하지 않는다.
