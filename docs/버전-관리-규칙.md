# 버전 관리 규칙

## 기준

- 현재 버전의 기준 파일은 저장소 루트의 `VERSION`이다.
- 파일명에는 `최종`, `수정`, `진짜최종` 또는 날짜별 복사본을 붙이지 않는다.
- 변경 이력은 Git 커밋으로, 공식 기준점은 Git 태그로 남긴다.
- Word와 Excel 문서의 변경 이유는 Excel 관리대장의 `변경기록` 시트에도 기록한다.

## 프로젝트 버전

프로젝트 전체 버전은 `MAJOR.MINOR.PATCH` 형식을 사용한다.

- `MAJOR`: 기존 보드 또는 통신 규격과 호환되지 않는 큰 변경
- `MINOR`: 새로운 기능이나 주요 설계 단계 완료
- `PATCH`: 기능을 바꾸지 않는 오류 수정과 문서 보완
- `-draft`: 아직 검토 또는 승인되지 않은 상태

예: `0.1.0-draft`, `0.1.0`, `0.2.0`, `1.0.0`

## 산출물별 버전

### 요구사항

- 초안은 `0.1-draft`부터 시작한다.
- 검토 중 내용 변경은 `0.2-draft`, `0.3-draft`처럼 올린다.
- 최초 합의된 요구사항은 `1.0`으로 고정한다.
- 합의 후 요구사항이 바뀌면 변경 이유와 영향 범위를 기록한다.

### 하드웨어

- 제작 전에는 H/W 리비전을 부여하지 않는다.
- 첫 번째로 발주하는 PCB는 `A0`이다.
- 호환 가능한 수정판은 `A1`, `A2`처럼 올린다.
- 커넥터·전원·인터페이스 등 호환성에 영향을 주는 큰 변경은 `B0`로 올린다.
- PCB silkscreen과 제조 산출물에 리비전을 표시한다.

### 펌웨어와 PC 도구

- 각각 독립적으로 `MAJOR.MINOR.PATCH`를 사용한다.
- 개발 중에는 `0.x.y`, 검증된 최초 릴리스는 `1.0.0`으로 한다.
- 장치 정보 응답과 시험 결과에 펌웨어 버전을 포함한다.

## Git 태그

검토 또는 제작 기준점에만 태그를 만든다.

| 태그 예시 | 의미 |
|---|---|
| `v0.1.0` | 요구사항 최초 확정 |
| `v0.2.0` | 시스템 구조 확정 |
| `v0.3.0` | 회로도 검토 완료 |
| `v0.4.0-hw-a0` | A0 PCB 발주 기준 |
| `v0.5.0` | 최초 펌웨어 Bring-up 완료 |
| `v0.9.0` | 통합 검증 완료 후보 |
| `v1.0.0` | 최종 요구사항과 검증 통과 |

## 작업 절차

1. 작업 전에 `VERSION`과 현재 Git 상태를 확인한다.
2. 하나의 설명 가능한 변경 단위로 작업한다.
3. Word와 Excel 파일을 닫은 뒤 Git에 추가한다.
4. 변경 이유가 드러나는 커밋 메시지를 작성한다.
5. 단계 검토가 끝난 경우에만 버전을 올리고 태그를 만든다.
6. 제조 자료와 시험 결과에는 사용한 H/W·F/W 버전을 함께 기록한다.
